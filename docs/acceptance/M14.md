## Decisions and notes

- **Keyframes per property**, as planned. An edit at the playhead keys exactly what it changed, and X and Y (and W and H) are keyed together, as Animate and Hype key "position": moving only X at frame 15 no longer lets Y drift on the way there (found with Worked Example 19.01).
- **A still object at frame 0 is simply changed.** Keyframes start when something is changed at a later frame; the first keyframe at frame 0 is made with it.
- **The playhead goes from 0 to the length** (the end shows the last pose); playback and the exports show frames 0 to length − 1, so a 3 s animation at 24 fps is 72 frames and 3.00 s. A whole-animation loop does not show the end and frame 0 one after the other.
- **Export through PNG frames, not a raw pipe.** The plan said raw RGBA streamed into FFmpeg. Frames written as PNG into the app's own folder are a few tens of KB each instead of up to 8 MB (1080p), use the file and job channels that already exist, and make the PNG sequence the same step. The IPC channel only accepts frames in that folder; the job removes them however it ends.
- **A GIF cannot hold 24 fps exactly** (its delays are in hundredths of a second). FFmpeg mixes delays of 4 and 5 hundredths, so 72 pictures still last 3.00 s, but the average frame rate reads 25 fps (measured). A GIF task check should therefore check the format, the size and the duration, not the frame rate.
- **A font size of 0 is allowed** (Task 1 grows the text from 0 px); nothing is drawn.
- **Task 2's letters** enter "along individual motion paths" in the workbook; motion paths are M15, so M14 checks straight moves. **Task 1.2's morph** is M15 too.
- **"Radius of 102 pixels"** (Task 1): the text says radius, so the circle is 204 × 204 (M13's decision), which also makes the end position (396, 196) the bottom-right corner. Figure 7.4 looks closer to 102 px across; Hype's W and H boxes may be what the book meant.
- **Send to Video mode** saves `Name.mp4` beside `Name.mvea`; sending again updates the same clip.
